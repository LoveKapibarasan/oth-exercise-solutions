position. On lookups, we compute the hash for the bitwise smaller position (minimum of the
actual and the mirrored position) and then check whether the entry’s key matches this bitwise
smaller position.

G. Opening Books
Problem:The top of the game tree (the first 10–12 moves) has the highest branching factor
and the positions require the deepest calculations. Evaluating these positions repeatedly during
gameplay is too slow for real-time applications.
Solution:Precompute anOpening Book (OB)for the early game.
Key Optimization: Asymmetric Generation
•Symmetric approach:Compute all valid moves for both players.
–At depth 12, there are≈16 million unique positions. Fully solving all of them takes
a considerable amount of time.
•Asymmetric approach:
– Bot’s turn:Only compute and store thesingle best move.
– Opponent’s turn:Compute responses forall valid moves.
–=⇒Reduces the state space (≈7·1·7·1·. . .+ 1·7·1·7·. . .move sequences)
while guaranteeing a perfect response to any opponent play. Generation time drops
to mere minutes or hours.
•Implementation Details:How do we do this in code? We use an outer function that
plays the first 12 moves asymmetrically. Every time it is the bot’s turn, we call our normal
negamaxsolver. Sincenegamaxsearches a huge tree, we can save every score it finds for
the first 12 moves directly into our opening book.
Storage Strategies:To store these positions, one could use aHash T able, which re-
quires a collision resolution strategy like open addressing with double hashing. Alterna-
tively, one can collect all positions found during anegamaxcall in anarray. At the end of
the call, these are appended to the opening book (an array again), sorted, and stripped of
duplicates. During actual gameplay, the bot can then efficiently query the opening book
using binary search.
In both strategies, one should use the opening book created so far during opening book
creation.
